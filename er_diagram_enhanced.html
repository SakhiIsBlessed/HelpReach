📋 ER Diagram Components & Relationships

Entity Primary Entity Key Attributes Relationships
USER 👤 Donor user_id, name, email, phone, location creates Donations, subscribes to Notifications
NGO 🏢 Organization ngo_id, name, email, address, registration_number receives Claims, uploads Documents, maintains Bank Accounts
DONATION 🎁 Core Entity donation_id, description, status, created_at contains Items, has Photos, can be Claimed
DONATION_ITEM 📦 Child Entity item_id, item_name, quantity, condition belongs to one Donation
DONATION_PHOTO 📸 Media photo_id, filename, filepath, uploaded_at belongs to one Donation
DONATION_CLAIM ✅ Interaction claim_id, status, claimed_at links Donation to NGO
NGO_DOCUMENTS 📄 Verification doc_id, filename, doc_type, uploaded_at uploaded by NGO
NGO_BANK_ACCOUNT 🏦 Financial bank_id, account_number, bank_name, ifsc_code maintained by NGO
PUSH_SUBSCRIPTION 🔔 Notification subscription_id, endpoint, p256dh, auth_key subscribed by User
EMAIL_LOG 📧 Audit Trail email_id, recipient_email, subject, sent_at logs all system emails
🔑 Key Terms Explained
PK (Primary Key): Unique identifier for each record (e.g., user_id)
FK (Foreign Key): Reference to another table's primary key (e.g., user_id in Donation)
UK (Unique Key): Value must be unique but not primary key (e.g., email)
||--o{: One-to-Many relationship (1 User creates many Donations)
||--||: One-to-One relationship (1 Donation contains 1 Item)
o{--||: Many-to-One relationship (Many Claims belong to 1 NGO)
📊 Relationship Analysis
USER creates DONATION (1 : Many): One user can create multiple donations over time

DONATION contains DONATION_ITEM (1 : 1): Each donation record contains one item entry (could be expanded to many)

DONATION has DONATION_PHOTO (1 : Many): One donation can have multiple photos from different angles

NGO receives DONATION_CLAIM (1 : Many): One NGO can claim multiple donations

DONATION claimed by DONATION_CLAIM (1 : Many): One donation can have multiple claims from different NGOs

NGO uploads NGO_DOCUMENTS (1 : Many): One NGO uploads multiple verification documents

NGO maintains NGO_BANK_ACCOUNT (1 : Many): One NGO can have multiple bank accounts

USER subscribes PUSH_SUBSCRIPTION (1 : Many): One user can have multiple device subscriptions
🔄 Data Flow in the System
1. Registration Phase: USER & NGO entities are created → NGO uploads NGO_DOCUMENTS → NGO adds NGO_BANK_ACCOUNT

2. Donation Creation Phase: USER creates DONATION → Adds DONATION_ITEM details → Uploads DONATION_PHOTO(s)

3. Notification Phase: System queries EMAIL_LOG → Sends emails to matching NGOs → Creates PUSH_SUBSCRIPTION

4. Claim & Verification Phase: NGO creates DONATION_CLAIM → System verifies NGO (checks NGO_DOCUMENTS) → Updates claim status

5. Completion Phase: Pickup instructions sent → DONATION_CLAIM status updated → DONATION marked complete
📝 Status Values by Entity
DONATION.status: pending, claimed, approved, rejected, completed, expired
DONATION_CLAIM.status: pending, approved, rejected, completed
NGO_DOCUMENTS.status: uploaded, verified, rejected, pending
✨ Design Notes
• All entities have timestamps (created_at, updated_at) for audit trails
• PASSWORD_HASH stored instead of plain text for security
• DONATION_PHOTO stores filename and filepath for flexible storage (local/cloud)
• EMAIL_LOG enables recovery and audit of all communications
• NGO_DOCUMENTS allows verification of organizational legitimacy
• PUSH_SUBSCRIPTION enables browser notifications without polling
